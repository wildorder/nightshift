In packages/execution/src/line/compose.ts the composer's only durable write is queue.settle, called once per batch from finish (line 404). A failing range's held entry is written there with repairs set to the first attempt (lines 741-754), and after that processDone (lines 340-347) increments lineage.repairs in memory and startNext launches the next repair job with no settle between attempts; LineQueuePort has no other write. Each replacement can spend two more repair jobs, and repeated replacements are unbounded. The two fixes so far addressed other paths (a rejected push recomposing from the repair commit, lastComposed, settleBatch) and did not persist consumed attempts. The fix is as the examiner states: persist each consumed attempt (and the last failure's words) before launching it, or rebuild the consumed budget from the run's durable repair jobs, and test replacement after a later attempt.

- **Upheld** by claude-fable-5-1 F-01 Settlement events become reportable facts before settlement commits, without a recovery/commit marker. Injecting failure on the second event append leaves record.parked empty but gatherReport already reports the first entry as parked. If retries are exhausted or the owner is replaced, the held batch is recomposed rather than replaying a persisted settlement; those prewritten events remain permanently and can describe a result that never settled. A takeover between the dry-run and update similarly allows events for a refused settlement. Persist a recoverable settlement intent and publish its facts only once committed (or use an atomic write), so Studio/report cannot treat partial attempts as completed results. on node_01M63151HG0BSF6D2ABKBSPBZR: The finding is right on the code, and the failure it describes is one the system's own design makes ordinary, not exotic.

What the code does. postLineSettle (apps/api/src/operations/line.ts) dry-runs settleBatch, appends one event per entry, and only then runs the conditional update. The event ids are derived from the batch (settleIds in packages/core/src/rules/line.ts: `${batchId}-c`, `${batchId}-p${i}`), and the event store treats an idempotency key as write-once within a run (packages/persistence/src/memory/index.ts append: an existing key returns the stored event, never overwrites). gatherLine (packages/core/src/report/report.ts) includes every parseable line.composed / line.parked event of the run, unioned with the record, event first; a parked event has nothing on the record to overlay or remove it.

Why it matters. The composer catches nothing around queue.settle (compose.ts: "a throw settles nothing and leaves the batch held"); the HTTP transport gives four attempts over about two seconds and then throws. A replacement owner is the same run at generation+1 (A-51, A-66), and takeBatch hands it back the same batchId. So after a partial append (or a takeover between the dry-run and the update, where applyLineChange refuses with stale_generation after the events are already stored), the replacement recomposes the same batch, possibly on a moved main, and settles with the same ids. Its appends hit the already-stored keys and return the stale events, so the run's durable history permanently records the first attempt's commit and parked entries, including a parked range and reason that never settled, while the record holds a different outcome. Once the record's window evicts the entry, the report and Studio show only the phantom. The report leads with exactly these sections, so acceptance criteria 1 and 3 are not met in this case.

The new tests cover only the happy retry (same body, same generation). Nothing covers the replacement or takeover path, which is the one the finding names. Two fixes have not changed the ordering or added a commit marker. The work should not land as it is: either publish the facts only once the record change commits (events after the update, or a settled marker the report requires), or make the event keys depend on the settlement's content so a different retry cannot be silently swallowed by the first attempt's write.
  Decision `dec_01M63A73BKWG7JYB8AB31A61A2`, made against checkpoint `ckpt_01M63A3R9KX28ZQW1T7WPWB2T1`.

## Stories

### US-01 A conflict starts a repair on the warm line machine and the line keeps composing everything that does not touch the same: done

- **Who:** The owner running several programs at once
- **Today:** When one program's range conflicts on the line, the owner holds the whole line for up to an hour while a resolver works, so every range queued behind it waits; with many programs, conflicts become the throughput limit.
- **Afterwards:** A conflict starts a repair on the warm line machine and the line keeps composing everything that does not touch the same files; only the colliding ranges wait, and a range that keeps failing is parked for its pull request instead of looping.
> "i want what scales. what moves us toward the futue scion vision. but i want it done elegantly not clumsily. what do you recommend"

Criteria: SC-01 met, SC-03 met. Strands: S-01, S-02.

### US-02 A repair is a job of the line's run, with its transcript, events, examination and decision in the Studio and the report,: done

- **Who:** The owner reading a line failure the morning after
- **Today:** A line repair leaves no Agent record, no events, no transcript and no machine log; the first line failure on foodfly was 'the resolver failed (exit 127)' and nothing else, and the machine that could have explained it was gone.
- **Afterwards:** A repair is a job of the line's run, with its transcript, events, examination and decision in the Studio and the report, and every machine's runner log is kept as an artifact, so any line failure can be read afterwards without anyone watching live.
> "do you have to monitor the error live, or can you troubleshoot after, will you have the right logging in place to look at a failure afterwards? because if that's the case, i'm just going to keep operating as-is and wait for this to appear again"

Criteria: SC-02 met, SC-04 met, SC-05 met. Strands: S-02, S-03.

### US-03 There is one way an agent is launched and recorded and one implementation of a machine's lifecycle, used by program runs: done

- **Who:** Whoever maintains Nightshift
- **Today:** The line has its own agent launcher, its own harness entry point and its own machine record and handlers beside the run's; the three bugs found on the line's first trial all lived in that copy.
- **Afterwards:** There is one way an agent is launched and recorded and one implementation of a machine's lifecycle, used by program runs and line runs alike; the line keeps only what is genuinely the line's: the queue, compositions, the push and the cap.

## Departures from the plan

**S-02 The composer in the root seat, repairs as engine jobs, the kept log**

- **The plan put the reservation set, the held queue and the per-lineage budget in compose.ts alone, with repairs landing where the composer wants via programBranch == line branch. In the code, the plane's settleBatch drops entries that are neither composed nor parked. The engine also integrates onto one program branch, and would push a landing to GitHub through its landing publisher.**
  Chose: A small plane change (S-01's area).
- LineRecord gains a durable `held` list. Settle can move batch entries into it. takeBatch takes only from the queue, can `release` named held entries to the queue front, and a newer generation's takeBatch releases all held entries.
- Queue entries and composition ranges carry a lineage `repairs` count that survives held, composition and rejected-push requeue.
- The live reservation and next-up logic stays in compose.ts.
- One repair is in flight per line at a time.
- Every repair starts from a local candidate merge (line head, range.upTo): for a conflict, the markers are committed. The repaired commit is merged onto the current line head.
- The engine's landing publisher is off for line runs, so the composer's bundle push stays the only way to GitHub.
  Why: This meets acceptance 3 and 4 and D-04/D-05 durably: no head-of-line blocking, and no budget reset through replacement or a rejected push. It keeps the whole range's content and any concurrent landings, and it adds no second path to GitHub. Both review rounds raised these issues, and they are folded into J3, J5 and J7.

## Definitions

- **Active seconds** (`active_seconds`): Seconds during which something was executing for the run, as recorded by the control plane. Idle gaps are excluded. Denominator: Runs with recorded activity intervals.
- **Agent time** (`agent_time`): Harness execution time of an agent, from its start to its end. It excludes verification, queueing and integration. Denominator: Agents with both a recorded start and end.
- **API-equivalent estimate** (`api_equivalent_estimate`): An estimate of what the measured tokens would cost at a price table's list rates. It is an estimate from a price table, not a bill, and subscription or negotiated pricing may differ. Denominator: Attempts with a price-table entry for their model and measured tokens; others are unpriced.
- **Combined estimate** (`combined_estimate`): The model estimate plus the machine estimate. It is a lower bound when either part is incomplete. Denominator: Runs with both parts measured count fully; the rest are listed as incomplete.
- **Completion lead time** (`completion_lead_time`): Time from a story or goal being planned to its work being delivered, as recorded on a completion checkpoint. Denominator: Completion checkpoints whose members all have recorded times.
- **Coverage** (`coverage`): How completely an attempt's resources were observed: complete, partial, unknown, legacy (route figures only) or missing. Missing evidence is never shown as zero. Denominator: All attempts in the selected population, tallied by coverage class.
- **Delivered outcomes** (`delivered_outcomes`): Jobs whose work was verified and integrated, counted once each however many attempts it took. Denominator: All jobs in the selected population, delivered or not.
- **Elapsed completion time** (`elapsed_completion_time`): Wall-clock time from the start of the run or story to its completion, measured on the clock; overlapping work is counted once. Denominator: Completed runs or stories only; unfinished ones are excluded and counted in the sample size.
- **Examination time** (`examination_time`): Time examiners and the helper routes serving them (answering, arbitrating) spent on examinations of the work. Denominator: Examination routes with a recorded start and end.
- **Examiner dispositions** (`examiner_dispositions`): How examiners' findings were resolved: upheld, rejected, fixed or still open. Denominator: Findings raised in the selected population.
- **First-attempt success** (`first_attempt_success`): Delivered jobs whose first attempt (attempt 1) was verified and integrated without a later attempt. Association with rework is not causation. Denominator: Jobs that reached a terminal state in the selected population; jobs still running are not counted.
- **Human verdict** (`human_verdict`): The person's binary verdict on whether a run worked, captured with its attribution. It is separate from deterministic verification and does not change recorded outcomes. Denominator: Runs that received a verdict; unrated runs have none.
- **Infrastructure estimate** (`infrastructure_estimate`): An estimate of the machine expense of runs executed on Nightshift-provisioned machines, from their utilization and a rate table. Denominator: Runs with a machine report; local runs have none and are absent, not zero.
- **Integration time** (`integration_time`): Time spent integrating verified work onto its target branch, after verification passed. Denominator: Integrated jobs with recorded integration intervals.
- **Provider-reported cost** (`provider_reported_estimate`): The dollar figure the provider or harness itself reported, kept apart from the price-table estimate and never summed with it. It is an estimate of spend, not an invoice. Denominator: Attempts whose harness reported a cost; others are unpriced.
- **Queue time** (`queue_time`): Time verification requests waited for the verification queue before they started running. Denominator: Verifications in the selected population that recorded a queue phase.
- **Rating coverage** (`rating_coverage`): The share of completed runs that carry a human verdict. Denominator: Completed runs in the selected population.
- **Review overhead** (`review_overhead`): Resources and time spent by examination and arbitration routes, shown beside the work they reviewed. It is not a measure of review quality. Denominator: Helper routes in the selected population compared with all routes.
- **Rework attempts** (`rework_attempts`): Attempts made after a node's first attempt: escalations and retries of the same node's work. Association with other factors is not proof of causation. Denominator: Attempts of jobs in the selected population; the first attempt of each job is not rework.
- **Rework by cause** (`rework_by_cause`): Rework attempts grouped by the cause recorded when the attempt was made (for example verification failure or examiner finding). An attempt with several causes appears under each. Denominator: Rework attempts with a recorded cause; those without one are counted as unattributed.
- **Run completion time** (`run_completion_time`): Time from a run's start to its completion, measured on the clock. Denominator: Runs that completed.
- **Sample size** (`sample_size`): How many rows matched a filter and how many there were in all, so a figure is read against its population. Denominator: Matched rows out of all rows before filtering.
- **Settlement time** (`settlement_time`): Time from an attempt's start until its node settled, including verification, queue and integration. It is longer than agent time. Denominator: Routing decisions that recorded a wall-clock figure.
- **Summed work time** (`summed_work_time`): The sum of every attempt's working time. It is not elapsed time: work overlaps, so the sum can exceed the clock time of the run. Denominator: Attempts with a recorded start and end; attempts without both add nothing and are counted as missing.
- **Cache-read tokens** (`tokens_cache_read`): Tokens served from the provider's prompt cache, where reported. Denominator: Attempts whose provider reports cache reads; others are not counted as zero.
- **Cache-write tokens** (`tokens_cache_write`): Tokens written to the provider's prompt cache, where reported. Denominator: Attempts whose provider reports cache writes; others are not counted as zero.
- **Input tokens** (`tokens_input`): Input tokens the provider reported, normalized to include cache reads and writes where the convention is known; an unknown convention is flagged and the raw figure kept. Denominator: Attempts with a measured input counter; attempts without one are counted in coverage, never as zero.
- **Output tokens** (`tokens_output`): Output tokens the provider reported for the attempts. Denominator: Attempts with a measured output counter; absent counters are not zero.
- **Reasoning tokens** (`tokens_reasoning`): Reasoning or thinking tokens, where the provider reports them apart from output. Denominator: Attempts whose provider reports reasoning tokens; others are not counted as zero.
- **Wait time** (`wait_time`): Time the run spent waiting rather than working: for a human, for capacity, or for a prerequisite, as recorded on the control plane. Denominator: Runs with recorded waiting intervals; absent intervals are unknown, not zero.
